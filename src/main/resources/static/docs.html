Contexto do Sistema

C4 Nível 1

O GestarAfeto é uma aplicação web de apoio organizacional ao acompanhamento pré-natal. Opera como um monólito Spring Boot com frontend React, acessado pela usuária via browser. Na Segunda Entrega a persistência passou a ser real: PostgreSQL como banco de produção/desenvolvimento, schema versionado por Flyway e histórico de dados via Hibernate Envers. Não substitui avaliação médica — é uma ferramenta de organização e rastreabilidade de informações.

Bounded Contexts — DDD

Domain-Driven Design

O sistema vive dentro do bounded context acompanhamento-prenatal, subdividido em quatro subdomínios de negócio, um subdomínio técnico transversal (Auditoria, introduzido na TP2) e um subdomínio futuro. A organização interna por domínio (e não por tipo técnico) preserva o isolamento e prepara o projeto para extração de microsserviços.

Arquitetura em Camadas

Layered Architecture

Cada requisição percorre as camadas de cima para baixo. Controllers não contêm regras de negócio. Services coordenam fluxos, abrem transações (@Transactional) e aplicam regras. Repositories Spring Data isolam o acesso ao banco. DTOs (records) evitam expor entidades JPA. A camada de Domínio é auditada pelo Envers, que escreve nas tabelas de histórico dentro da mesma transação.

Estratégia de Persistência

Segunda Entrega

A camada de persistência é real e versionada. O Flyway é a fonte de verdade do schema nos perfis PostgreSQL; o Hibernate roda em ddl-auto=validate — ou seja, valida o mapeamento contra o schema existente, mas nunca altera tabelas em produção. Cada entidade mutável carrega @Version para controle de concorrência otimista. Perfis dedicados isolam ambientes de desenvolvimento, teste e produção.

Perfis de execução
PerfilBancoFlywayddl-autoUso
dev🐘 PostgreSQL (Docker Compose)✅ habilitadovalidateDesenvolvimento local com banco real
prod🐘 PostgreSQL (variáveis de ambiente)✅ habilitadovalidateProdução
dev-h2💧 H2 em memória (modo PostgreSQL)❌ desabilitadocreate-dropDesenvolvimento rápido sem Docker (seed via DataInitializer)
test💧 H2 em memória (modo PostgreSQL)❌ desabilitadocreate-dropTestes de repositório rápidos (@DataJpaTest)
Decisões de projeto
  • Flyway como fonte do schema — DDL explícito e revisável, migrations imutáveis versionadas no Git.
  • ddl-auto=validate — o Hibernate não improvisa o schema; divergências falham no startup.
  • H2 em modo PostgreSQL nos testes — sintaxe compatível, feedback rápido, sem depender de Docker.
  • Testcontainers — evidência de compatibilidade com PostgreSQL real quando há Docker disponível.
  • DTOs (records) — a API nunca serializa entidades JPA diretamente, evitando lazy-loading acidental.

Migrations Flyway

Schema Versionado

Quatro migrations descrevem toda a evolução do schema, aplicadas em ordem e registradas na tabela flyway_schema_history. Migrations já aplicadas são imutáveis: qualquer mudança futura entra como V5, V6…

VersãoArquivoConteúdo
V1create_core_tables.sqlCria gestantes, procedimentos_prenatal, itens_checklist_gestante e consultas_prenatal, cada uma com version (lock otimista).
V2create_constraints_and_indexes.sqlChaves estrangeiras, UNIQUE(gestante_id, procedimento_id), checks de domínio e índices de consulta.
V3insert_default_procedures.sqlSeed idempotente dos 23 procedimentos base do protocolo de pré-natal.
V4create_audit_tables.sqlTabela revinfo + tabelas *_aud do Envers, com FK para revinfo(rev).
ℹ️
Nos perfis dev-h2 e test o Flyway fica desabilitado e o Hibernate cria o schema com create-drop — isso mantém os testes de repositório rápidos. A validação das migrations contra o PostgreSQL real é coberta pelo MigrationIntegrationTest com Testcontainers.

Integridade & Performance

Gerenciamento de Dados

A integridade é garantida no banco (constraints) e na aplicação (Bean Validation + regras de negócio). A performance é tratada com carregamento LAZY, @EntityGraph para evitar N+1 e paginação nas listagens que crescem.

🛡️ Integridade
@Version em todas as entidades mutáveis (lock otimista → HTTP 409)
UNIQUE(gestante_id, procedimento_id) impede item de checklist duplicado
Check: semana_gestacional entre 1 e 42
Check: peso > 0
Check: semana inicial ≤ semana final do procedimento
Check: status REALIZADO exige data_realizacao
FKs gestante_id / procedimento_id com integridade referencial
Bean Validation (@NotBlank, @NotNull) na borda da API
⚡ Performance
@ManyToOne(fetch = LAZY) em todos os relacionamentos
@EntityGraph carrega gestante/procedimento sob demanda (evita N+1)
Listagens paginadas: Page<T> + Pageable
Índice idx_consultas_gestante_data_desc para histórico ordenado
Índices idx_checklist_gestante_status e idx_procedimentos_ativo_tipo
DTOs enxutos evitam serializar grafos inteiros

Auditoria & Histórico de Dados

Hibernate Envers

O histórico de mudanças é implementado com Hibernate Envers. Cada entidade anotada com @Audited gera uma tabela espelho *_aud. A cada transação que insere, altera ou remove um registro, o Envers grava uma revisão (linha em *_aud + referência a revinfo) com o tipo da operação (ADD, MOD, DEL), permitindo reconstruir o estado do dado em qualquer ponto do tempo — essencial para auditoria e rastreabilidade.

Como funciona
  • Entidades auditadas: Gestante, ProcedimentoPreNatal, ItemChecklistGestante, ConsultaPreNatal.
  • AuditoriaRevision (@RevisionEntity) mapeia a tabela revinfo — número da revisão + timestamp.
  • store_data_at_delete=true: mesmo em exclusões, o último estado é preservado no histórico.
  • AuditoriaService usa AuditReaderFactory.get(em).createQuery().forRevisionsOfEntity(...) para ler as revisões.
  • Endpoint: GET /api/auditoria/{entidade}/{id} → aceita gestante, procedimento, checklist, consulta.
// application.properties — configuração do Envers spring.jpa.properties.org.hibernate.envers.audit_table_suffix=_aud spring.jpa.properties.org.hibernate.envers.store_data_at_delete=true
Resposta do endpoint de histórico

Sequência — Concorrência (Lock Otimista)

@Version · Integridade

Duas usuárias editam a mesma gestante simultaneamente. A coluna @Version garante que a segunda gravação, baseada em uma versão desatualizada, seja rejeitada com OptimisticLockException — traduzida pelo GlobalExceptionHandler em HTTP 409 Conflict, evitando perda silenciosa de dados (lost update). 

sequenceDiagram
    actor U1 as 👩 Usuária A
    actor U2 as 👩 Usuária B
    participant Service as GestanteService
    participant DB as 🐘 PostgreSQL

    Note over U1,U2: Ambas carregam a mesma gestante (version = 5)

    U1->>Service: atualizar(id, dadosA)
    Service->>DB: UPDATE gestantes SET ..., version=6 WHERE id=? AND version=5
    DB-->>Service: 1 linha afetada ✓ (agora version = 6)
    Service-->>U1: 200 OK

    U2->>Service: atualizar(id, dadosB) [ainda com version = 5]
    Service->>DB: UPDATE gestantes SET ..., version=6 WHERE id=? AND version=5
    DB-->>Service: 0 linhas afetadas ✗
    Service-->>U2: OptimisticLockException → 409 Conflict
    Note over U2: Recarregar dados atualizados e repetir a edição

Motor de Regras

Regra de Negócio

MotorDeRegrasAlerta é uma classe sem estado e sem acesso a banco, o que a torna testável isoladamente. Ela estima a semana gestacional e classifica cada item pendente.

Semana gestacional: calculada a partir da DUM (semanas completas + 1). Sem DUM, é derivada da DPP (total − semanas restantes). Sem nenhuma das duas, as regras baseadas em janela não se aplicam. O resultado é limitado a 1..42.

Situação do itemTipoPrioridade
PRECISA_REVISARREVISAO_SOLICITADAALTA
PENDENTE, semana atual > semana finalPROCEDIMENTO_ATRASADOALTA se obrigatório, senão MEDIA
PENDENTE, semana atual dentro da janelaPROCEDIMENTO_PENDENTEMEDIA se obrigatório, senão BAIXA
PENDENTE, janela começa em até 2 semanasJANELA_PROXIMABAIXA
REALIZADO ou NAO_SE_APLICA—alerta existente é resolvido

Reconciliação. AlertaService.avaliar compara o resultado do motor com o que já está gravado, pela chave (origemId, tipo):

Configuração distribuída. Os parâmetros do motor são externalizados (antecedencia-semanas, semanas-gestacao-total, alertar-nao-obrigatorios). Com um Config Server no ar, um POST /actuator/refresh reaplica os valores sem reiniciar o serviço — o rebind acontece sobre a mesma instância do bean, então o motor passa a usar os novos limiares imediatamente. O prefixo optional: garante que a ausência do Config Server nunca impeça a inicialização.

Sincronização por eventos. O ChecklistService não conhece alertas: apenas publica ChecklistAlteradoEvent. O listener reage em AFTER_COMMIT, garantindo que o microsserviço só seja chamado depois que a alteração está gravada — e nunca dentro de uma transação aberta.
